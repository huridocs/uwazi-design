## 2. Selection

Existing multi-select (none for library entities):
- `librarySelectedEntityIdAtom` (`atoms/library.ts:147`): SINGLE id, means "previewed in the drawer". Cleared by the reset atom at `:669`. `handleSelect` (`LibraryView.tsx:590`) sets it and focuses the entity for preview (mobile: opens the full entity instead).
- Multi-select patterns to copy: `FilesView.tsx:38` `useState<Set<string>>` with toggle (`:75`) and per-subset select-all (`:83`); `ImportCSVView.tsx:18` same; `components/import-csv/ImportTable.tsx:87` and `components/files/FileTable.tsx:225,275,280` render the shared `Checkbox` (`components/shared/Checkbox.tsx`, native input, `ariaLabel`) in a leading column plus a header select-all. Local `useState`, not atoms, and no shift/ctrl handling anywhere (grep for `shiftKey|metaKey|ctrlKey` in components/files, FilesView, DataTable: none).
- Figma has "EV - Files (Table Multi-select)" with a bulk action bar, "Selected 2 of 4" (`screens.md:152`).

Row click today (stretched primary button pattern, per CLAUDE.md):
- `EntityCard` (`components/library/EntityCard.tsx:282-296`): `primaryAction` = `absolute inset-0` `<button aria-pressed={selected} aria-label="Select {title}">` whose click does `e.stopPropagation(); onSelect(id)`; the container also has a plain `onClick={() => onSelect(id)}` (`:311`, `:399`). Nested controls ("Open" `:432`, connection badge) stop propagation. Handler receives only `id`, not the event, so modifier keys are lost.
- `DataTable` (`components/shared/DataTable.tsx:167-203`): row has `onClick`, and a stretched button in an absolute cell calls `onRowClick(row)` with the event stopped. `isRowSelected` drives `bg-parchment`. No checkbox column; `onRowClick(row)` gets no event either.
- `LibraryView.tsx:957` (cards) and `:979-981` (table) wire `selected={selectedId === e.id}` / `isRowSelected` / `onRowClick={(e) => handleSelect(e.id)}`.

Where modifier-click and range would hook, per surface (all currently funnel to `handleSelect(id)`):
- **Cards**: `EntityCard` `primaryAction` onClick and container onClick (`:290`, `:311`, `:399`); needs the event passed up (`onSelect(id, ev)`), and a `selectedIds` prop. `EntityCard` is `memo`; a Set prop changes identity on every toggle, so pass a per-card boolean derived from a stable Set ref, or keep it in an atom read via `selectAtom`.
- **List table**: `DataTable` `onRowClick` (`:177`, `:199`); either add an optional `onRowClickEvent`/`selectable` API or a Checkbox column via `columns` (the table is column-configurable from Display; a leading checkbox column fits the FileTable pattern). Range needs a stable row order: `shown` (first 120 of `filtered`), so range can be computed from `filtered` indexes, not DOM.
- **Timeline**: `LibraryTimelineView.tsx` has several layouts: `SpineLayout` (`:666-700`, stretched button + container `onClick`), rail/density/list layouts (`onSelect` at `:319`). Range order = date order in that layout, differs from `filtered` order, so "range" must be defined per layout or on the sorted list used by that layout. Density bars filter, not select.
- **Map**: pins open a cluster (`LibraryMapView.tsx:192` `open(c)`), the cluster drawer (`LibraryClusterDrawer.tsx:57`) lists `EntityCard layout="list"` with `selected={false}`, `onSelect={() => setSelectedId(e.id)}`. Multi-select should live in the cluster drawer list; "select all in cluster" is a natural action. A map marker itself is not an entity row.
- **Results** (`ResultsMainView.tsx`): grouped card title button (`:493`), passages row button (`:913`), spine row button (`:1084`); tree via `RelationshipGroupedCard`. Range order = rank order in `entities`; the passages layout has several rows per entity, so selection must key by entity id, not row.
- Selection scope questions to settle: does it survive filter/sort/query changes, and view switches (in `clearLibrarySearchAtom`-style resets)? Entities hidden by a filter would still be "selected" unless pruned. "Select all N" must mean `filtered`, not `shown`.

## 3. Editing

- Single-entity edit: `views/MetadataView.tsx`. `MetadataEditBody` (`:220`) holds local state only: `titles`, `fields` (per language, `useState` at `:284`), `templateId` (`:305`), `connections` (`:571`). `updateField(id, value)` (`:401`) writes into that local `fields` array (creating a missing field); `updateFieldFor` (`:420`) per language. Validation via `utils/validation.ts` on blur/save.
- **Edits do NOT persist.** `handleSave` (`:376`) validates, waits 800 ms and calls `onSave()`, which the caller sets to `() => setEditing(false)` (`:98`). No atom, no `entitiesAtom` write, nothing reaches the record. (`title.includes("[fail]")` simulates failure.) Any bulk edit therefore needs a new persistence layer first. That also relates to the open handoff item "lost edit from the drawer": the code does not remove edits, it never stores them.
- **Template change is presentational** (`:305` comment): "this prototype keys profiles off the seeded type, so picking another does not re-shape the entity". `TemplatePicker` (`:1375`) reads `entityTypesAtom`.
- Where entity data lives:
  - Mock ("Sample"): `entitiesAtom` (`atoms/entities.ts:6`, seeded from `data/entities.ts`) is the only writable entity list; only `CreateRelationshipModal` appends to it (grep). Field values are in `data/entityProfiles.ts` / `data/entityMetadata.ts` (per-language `MetadataField[]`, keyed by entity id), not in `Entity`.
  - CEJIL: raw JSON under `public/cejil-data` fetched once (`data/cejil/load.ts`), held in module state, adapted to `Entity[]` ONCE and cached in a module variable (`data/cejil/adapt.ts:443-446` `_libraryEntities`). Profiles built on demand by `buildCejilProfile` (`profile.ts:588`). `libraryEntitiesAtom` (`atoms/dataSource.ts:24`) just returns the cached array. It is not in any atom, so writes there need an overlay layer (e.g. a per-id overrides atom merged at read), or the cache and indexes (search index, `foldedFieldsCache` WeakMap keyed by Entity object) would go stale/fail to see edits.
  - Artworks: bundled TS (`artworkLibraryEntities()`), same shape as CEJIL, no atom.
- Template/property model:
  - App-side: `EntityProfile` (`data/entityProfiles.ts`) with `metadata[lang]: AnyMetadataField[]`; `deriveTemplateStructure(profile, language)` (`utils/templateStructure.ts:54`) returns `{header, fields, body, inherited}`. Field types: `text | date | link | country | multiline | file-list | media` plus `relationship` (`data/metadata.ts:10`, `:53`). There is no select/multiselect field type on the profile; thesaurus values are rendered by label (`ThesaurusValueLabel`, `utils/thesauri.ts` label→parent map).
  - Raw CEJIL templates (`data/cejil/templates.ts`) do carry Uwazi property types and `content` = thesaurus id (`select`, `multiselect`, `relationship`, `multidate`, `nested`, `geolocation`, `markdown`, `media`, `preview`...). Settings-side property list (`data/settings.ts:95-112`) has `type`, `required`, `filterable`, `showInCard`.
  - Common properties across N entities of mixed templates: computable as the intersection of `(name/id, type, content)` over each entity's template properties (`cejilTemplates[].properties` for CEJIL, with `commonProperties` title/creationDate/editDate always shared; for mock, intersect `profile.metadata[lang]` by `id` + `type`). Entity → template = `typeId`. For CEJIL only a subset of template properties is materialised on `Entity` (`fields`, `searchFields`, `descriptors`, `inherited`), so the authoritative source for the editable set is the raw entity metadata / `buildCejilProfile`, not `Entity`. Relationship and inheriting fields are read-only in the edit body (derived), so they'd be excluded from bulk edit.
- Copy From (`utils/copyFrom.ts`, `atoms/copyFrom.ts`, `CopyPreviewSection`) is the existing "write a value from entity A into entity B's edit form" mechanism, single-target and staged in the form; it already computes which properties are copyable between templates (`copyFrom.ts:151` exclusion list) and is the closest precedent for cross-template property matching.

## 4. Thesauri

- Model: Uwazi shape `{ id, label, values? }`, one nesting level (group with `values`). App seed: `data/settings.ts:139-168` (`SettingsThesaurus`, `ThesaurusValue`, `seedThesaurusValues`), CEJIL dump `data/cejil/thesauri.ts` (`cejilThesauri`, 8 thesauri: Estado, Descriptores, Tipos, Sexo, Tipo de declaracion, Tipo de audiencia, Formato de la Audiencia, Tipo de diligencia) with adapter `data/cejil/settingsAdapt.ts` (`cejilThesaurusValues`).
- Where select values come from: property `content` = thesaurus id (raw CEJIL templates). In the app, entity values are stored as the child's LABEL (`utils/thesauri.ts` header comment); the record shows them through `ThesaurusValueLabel`; filters via `FacetSection`/`utils/libraryFacets` (descriptors facet on `Entity.descriptors`). No component picks a value from a thesaurus for editing: the edit body has no select/multiselect editor (fields are text/date/link/multiline).
- Settings screens: `components/settings/pages/ThesauriPage.tsx` (list: local `useState` of thesauri, add/delete with confirm) and `ThesaurusEditor.tsx` (name + items, groups, drag reorder, dirty check). Create-at-runtime: only as UI. `ThesaurusEditor.save` (`:110`) pushes a "saved"/"created" toast and closes; nothing is stored, and `ThesauriPage` state is local and re-seeded on remount. So a value or a whole thesaurus cannot really be created at runtime today; a bulk "add value to select" flow would need a thesaurus store (atom) that both Settings and the edit body read.
- Delete message in `ThesauriPage.tsx:70` states "Properties using it will fall back to free text", which is Uwazi's real behaviour but not modelled.

## 6. Real Uwazi behaviour

From the repo and memory files only: `uwazi-product.md` says CSV import uses pipe-delimited multi-values and multilingual columns; ZIP batch PDF import; "Library views: Card, Table, Map". `screens.md:152` records the Figma Files multi-select bulk bar. Neither says anything about library multi-select, multi-edit or export of a selection.

From general knowledge of Uwazi (NOT verified in this repo, treat as assumption; check against the live app or docs before designing): the library lets editors select multiple entities (checkbox / select-all in the sidebar area), and the sidebar then offers bulk actions such as multi-edit (properties common to the selected templates, applied to all), publish/unpublish, delete, and export CSV of the current search results (Settings → export is via the library "Export CSV" action for the current search, not limited to a selection). Exact rules (whether mixed templates are allowed for multi-edit, which property types are supported, whether it keeps values of untouched fields) need confirming.

## 7. Risks

- **Perf, 4,398 CEJIL cards**: only `DISPLAY_STEP = 120` cards are mounted (`LibraryView.tsx:112`); "select all" must operate on `filtered` ids without mounting. A `Set<string>` in local state re-renders `LibraryView` (huge component, four full-corpus memos hang off its render) on every toggle. Prefer a jotai atom per-id (`atomFamily`/`selectAtom`) or a ref-backed store so only the affected card re-renders; keep `EntityCard` `memo` effective (it takes the deferred query as a prop already; don't add a per-render Set/callback prop). Shift-range needs stable index over `filtered`.
- **filterState memo rule** (CLAUDE.md): selection must not enter `filterState` or any dependency of `matchTypeBase`/`filtered`/`searchMatchCount`/brush memos, or every toggle recomputes full-corpus passes. Keep selection separate; a "selected only" filter, if wanted, has to be keyed by content (`ids.join`) and will cost a pass.
- `ResultsBody` is `memo` and `ResultsMainView` re-snippets on `entities/visible/layout` change; selection props to them need stable identity or a selection atom read inside the row.
- **Edit persistence**: nothing persists, and CEJIL/artworks entities are module-cached and adapter-built. Bulk edit on CEJIL needs an override layer merged into `libraryEntitiesAtom` and invalidation of search caches (`foldedFieldsCache`, `docPagesCache`, search index memo), or edited values won't be searchable/filterable.
- **Mixed templates**: only the intersection of `(id, type, thesaurus content)` is editable; relationship/inherited/derived and `file-list`/media fields must be excluded; language-specific values (per-language `fields`) multiply the write surface.
- **Thesaurus writes**: no store. A bulk set on a select with a value not in the thesaurus has nowhere to create it.
- **a11y of selectable cards**: current pattern is one stretched button with `aria-pressed` that means "previewed". Reusing it for multi-select overloads one control with two meanings (preview vs checked). Likely needs a separate checkbox control per card/row (real `<input type=checkbox>` with `Select {title}` name, visible on hover AND focus-within per the hover-revealed-actions rule, and always visible in selection mode), a count in an `aria-live="polite"` region, and keyboard equivalents for range (Shift+Arrow / Shift+Space). Selected state must not introduce a new colour (rule: `bg-parchment`; the "preview" selected state already uses it, so "checked" vs "previewed" needs a non-colour cue, e.g. the checkbox). Rows with nested controls must not become `role="button"`.
- **Layout shift**: the footer bar must not grow/shrink when a selection begins; keep it mounted at fixed `h-12` and swap contents (the ToolsActionBar tint approach is fine), and never mount a count row inside the scroll lane.
- **Mobile**: the footer action buttons are `hidden sm:flex`; `handleSelect` on mobile opens the full entity instead of previewing, so a selection mode needs its own entry point there.
- **Hidden selection**: selected ids outside the current filter/query stay selected unless pruned or shown ("3 selected, 1 hidden by filters"); destructive or bulk actions on unseen entities is the main correctness risk.
- **Draft/preview interplay**: single selection (`librarySelectedEntityIdAtom`) drives the right drawer; with multi-select the drawer has to show a bulk panel instead, which changes `drawer` selection at `LibraryView.tsx:1104`.

## 8. Recommendation

1. Decide persistence first (an entity overrides atom merged into the Library list, plus a thesaurus store); without it, bulk edit is a toast.
2. Build selection as a separate atom from `librarySelectedEntityIdAtom`, id-keyed, outside `filterState`, with an explicit checkbox control per card/row and event-aware `onSelect(id, ev)` for shift/ctrl.
3. Start with the actions that don't need persistence: Export CSV of selection (serializer + download) and select-all/clear in the footer bar; then bulk edit limited to text/select/multiselect properties common to the selected templates.

Not verified: anything in a browser; real Uwazi bulk-edit rules (section 6); whether `handleSelect` on the Timeline density/rail layouts is reachable for multi-select.

## 9. Addendum: what the drawer renders for a map cluster

- Component: `components/library/LibraryClusterDrawer.tsx` (`LibraryClusterDrawer`, whole file ~65 lines). Header (`:29-46`): MapPin, `cluster.label`, "N entities", an X button (`aria-label="Back to filters"`) that sets the cluster atom to null. Body (`:48-62`): `<ul>` of `EntityCard layout="list" as="li"`, one per id, `selected={false}` always, `onSelect={() => setSelectedId(e.id)}`, `onView={() => openEntity(e.id)}`, `query` = raw committed `libraryQueryAtom`.
- State atom: `librarySelectedClusterAtom` (`atoms/library.ts:218`), type `LibraryCluster { label: string; ids: string[] }` (`:212-217`). Set by the map pin click in `LibraryMapView.tsx:126-134` (`open(c)`): a 1-entity pin sets `librarySelectedEntityIdAtom` directly, a multi-entity pin sets the cluster and clears the selected id. Cleared by the reset atom at `atoms/library.ts:670`.
- Mounting: `LibraryView.tsx:1104-1110`: `drawer = selectedId ? <EntityDrawerPreview/> : selectedCluster && viewMode === "map" ? <LibraryClusterDrawer/> : filtersDrawer`. So a selected entity takes precedence; closing the preview returns to the cluster list because the cluster atom is untouched. The cluster drawer only shows in map view (`viewMode === "map"` guard), so a list of ids in any other view mode would need that guard changed.
- How a row opens an entity: `EntityCard` stretched primary button / container click -> `onSelect` -> `setSelectedId(id)` (previews in the same drawer), and the card's "Open" button -> `openEntityAtom` (full entity view). Differences from the Library grid: the grid uses `handleSelect` (`LibraryView.tsx:590`), which also calls `focusForPreview(id)` (focuses the entity for the preview's Relationships/Files/Document tabs) and, on mobile, opens the full entity. The cluster drawer bypasses `handleSelect` (writes the atom directly), so previewing from a cluster does not focus the entity for the scoped tabs and mobile behaviour differs. Worth routing through one handler if the same body serves multi-selection.
- Gaps for reuse as a multi-selection body: it resolves ids via `getEntity(id)` (`data/entities.ts:463`, filters out misses silently), it takes ids only (no total/hidden count), `selected` is always false, it renders every id with no cap or windowing (a 400-entity selection mounts 400 `EntityCard`s; the Library grid caps at 120), the title is `cluster.label` (a place name) with a map pin icon, and there is no per-row remove or bulk action slot. To serve a selection: generalise `LibraryCluster` (or add a sibling atom `{label, ids}`), lift the guard from `viewMode === "map"`, use `handleSelect`, add a windowed list (`DISPLAY_STEP`-style "show more"), and give the header a remove-from-selection X and the bulk action slot. Selection ids must also not collide with the single `selectedId` precedence: an open preview hides the list until closed.

## 10. Addendum: permissions and share

- Component: `components/share/ShareEntityModal.tsx` (479 lines), mounted from `components/relationships/DrawerActionBar.tsx:53-63` (entity drawer) and `views/MetadataView.tsx:129-134` (metadata read body). Props are only `{ open, onClose }`; the modal reads `focusedEntityIdAtom` for the title (`:70-71`), so it always describes the FOCUSED entity, not a list of ids.
- Data model (all local, none stored): `Visibility = "private" | "published"` (`:19`), `AccessLevel = "read" | "write"`, `Member { id, label, level }` (`:22-26`). State is `useState` (`visibility`, `members`, `dirty`), reset from constants each time `open` flips true (`:85-94`): visibility "private", members = the first seed user at "read" (`INITIAL_MEMBERS`, `:34`). Users/groups come from `seedUsers`/`seedGroups` (`data/settings.ts`); the "Add" lookup matches an exact username, email or group name (`findCollaborator :44-64`), error "No user or group found". Header comment (`:66`): "Static Share UI synced with Entity V2 Share modal — no permissions API".
- Save/Discard (`:328-346`): when `dirty`, "Discard changes" and "Save changes" both just call `onClose`; nothing is written. So per-entity permissions do not exist in the prototype as data.
- The only stored share-like data: `Entity.published?: boolean` (`data/entities.ts:79`), seeded ~80% true (`:290`, `:416`, `seededPublished`). It is read by the Library's Published/Restricted facet (`utils/libraryFilter.ts:57,215-217`, `wantPublished`/`wantRestricted`). The modal's "Published" toggle does NOT write it, and it is not initialised from it (always starts "private"), so modal and facet disagree for a published entity. No per-user/group ACL field exists on `Entity`.
- For bulk share/publish: needs (a) `published` and an ACL (`permissions: {id, type: user|group, level}[]`) on the entity via the same overrides layer as bulk edit, (b) the modal to take `ids: string[]` (title becomes "N entities", members merged with mixed-level display), (c) the facet to read the overridden value; CEJIL/artworks entities are cached adapter output (see 3), so `published` overrides need the same merge.
